# 코콤 월패드 Homenet2MQTT 전환기: 거실 난방만 꺼져 보이던 이유와 환풍기 연동

- 작성일: 2026-11-20
- 상태: 초안
- 원본 작업 기록: [2026-11-20 h2m 코콤 Room 0 난방·조명·환풍기 작업](../docs/history/2026-11-20-h2m-kocom-heater-light-fan.md)
- 확인한 환경 / 버전: Home Assistant OS, Homenet2MQTT 애드온 v3.4.0, 코콤 월패드(RS485-TCP 게이트웨이 1대)
- 발행일 / URL: 미발행

## 시작한 이유

코콤 월패드를 Home Assistant에 연결하려고 처음에는 HACS 커스텀 통합을 썼다. 그런데 잘 동작하지 않아 Homenet2MQTT(h2m) 애드온으로 옮겼다.
옮기고 나서 문제가 세 가지 남았다.

- 거실(0번 방) 난방만 Home Assistant에서 자꾸 꺼짐으로 바뀌었다. 다른 방 난방은 멀쩡했다.
- 설정을 정리하다가 거실 조명 하나를 실수로 지웠다.
- 예전 통합에서는 되던 환풍기 제어가 h2m에서는 되지 않았다.

이 글은 세 문제를 패킷 로그와 h2m 소스로 확인하고 고친 과정을 정리한다.

## 환경과 준비

- 월패드 메인 RS485 라인에 RS485-TCP 게이트웨이 1대를 연결했다.
- h2m은 Home Assistant 애드온으로 설치했다. 브릿지 하나(`kocom_main`)가 Mosquitto에 MQTT 디스커버리로 엔티티를 등록한다.
- 엔티티는 h2m 갤러리의 코콤 조명·난방 템플릿으로 만들었다.
- 모든 수정은 h2m 웹 화면의 엔티티 YAML 편집기에서 했다. h2m은 저장할 때마다 설정 파일을 자동 백업한다.

## 막혔던 부분과 해결

### 1. 거실 난방만 꺼짐으로 보이는 문제

h2m 대시보드의 최근 활동을 보니, 명령을 보낸 적이 없는데도 거실 난방의 현재온도·목표온도·모드가 같은 순간에 `0 / 0 / off`로 바뀌었다.
그런데 월패드에서는 난방이 계속 정상 동작하고 있었다. 실내온도 0도는 실제로 나올 수 없는 값이기도 하다.
그래서 실제 보일러가 꺼진 게 아니라 **h2m이 상태를 잘못 읽은 것**으로 봤다.

해당 엔티티의 패킷 로그에서 그 순간 들어온 패킷 두 개를 찾았다.

```text
AA55 30DC 00 36 00 01 00 20 00 00 00 00 00 00 00 00 63 0D0D
AA55 30DC 00 36 00 01 00 3C 00 00 00 00 00 00 00 00 7F 0D0D
```

코콤 패킷 구조로 읽으면, 둘 다 0번 방 온도조절기(`36 00`) 앞으로 온 패킷이다. 다만 세부 명령이 `0x20`, `0x3C`이고 값 8바이트가 전부 0이다.
갤러리 난방 템플릿의 상태 조건은 `30 D? 00 36 00`까지만 비교하고 세부 명령은 보지 않는다. 그래서 이 패킷도 상태 보고로 받아들여 0도·꺼짐으로 덮어썼다.
같은 형태의 패킷이 1~3번 방에서는 보이지 않았다. 거실만 이상했던 이유가 여기 있었다.
두 패킷이 정확히 무슨 의미인지는 확인하지 못했다.

해결은 "목표온도 바이트가 0인 패킷은 무시"하는 예외 한 줄이다.
정상 상태 패킷은 난방을 꺼도 목표온도(최소 5도)를 그대로 싣고 오기 때문에, 0은 정상 상태에서는 나오지 않는다.

```yaml
# h2m > room_0_heater 엔티티 YAML의 state 부분
state:
  data: [0x30, 0xD0, 0x00, 0x36, 0x00]
  mask: [0xFF, 0xF0, 0xFF, 0xFF, 0xFF]
  except: [{index: 10, data: [0x00]}]
```

h2m 소스(`packages/core/src/utils/packet-matching.ts`)를 보면, `state`에 `index`가 없을 때 `except`의 인덱스도 헤더(`AA 55`) 뒤부터 센다.
그래서 `index: 10`이 전체 패킷 기준 12번째 바이트, 즉 목표온도 자리다.
반영 전에 이 매칭 규칙을 Python으로 재현해서 실제 문제 패킷 두 개와 정상 패킷 형식에 돌려봤다. 문제 패킷만 걸러지는 것을 확인했다.

한 가지 더 있었다. 코콤 온도조절기는 상태를 주기적으로 보내지 않고 값이 바뀔 때만 보낸다.
그래서 수정 직후에는 이전에 잘못 들어간 `0 / off`가 그대로 남아 있었고, 온도를 한 번 바꾸고 나서야 정상 값이 들어왔다.

### 2. 실수로 지운 조명 복구

h2m 화면에서 엔티티를 지우면 지우기 직전 설정이 `entity_delete` 백업으로 남는다.
백업 목록에서 해당 조명이 남아 있는 마지막 백업을 찾아 그 엔티티 블록만 다시 추가했다.
백업 전체를 복원하면 일부러 지운 콘센트·도어벨 엔티티까지 같이 살아나기 때문이다.

코콤 조명은 한 방의 조명들을 한 패킷으로 함께 제어한다. 그래서 1번 조명 명령에도 2번 조명의 현재 상태가 실린다.
복구하기 전까지는 1번 조명을 누르면 2번 조명이 꺼진 값으로 같이 전송될 수 있으니 주의해야 한다.

### 3. 환풍기 연동

예전 h2m 백업에 환풍기 설정이 남아 있었다. 비교해보니 명령 패킷의 목적지와 출발지가 반대로 들어가 있었다(`30 BC 00 01 00 48 …`).
예전에 환풍기 제어가 됐던 HACS 통합(lunDreame/kocom-wallpad)의 명령 생성 코드를 확인했다. 이 코드는 목적지에 환기 장치(`48 00`), 출발지에 월패드(`01 00`)를 쓴다.
이 형식으로 환풍기 엔티티를 새로 만들었다.

| 동작 | 값 바이트 |
| --- | --- |
| 켜기 | `11 00 00` |
| 끄기 | `00 00 00` |
| 풍량 1·2·3단 | `11 00 40` / `80` / `C0` |
| 모드(환기·자동·바이패스·취침) | `11 01` / `02` / `03` / `05` `00` |

Home Assistant에서 환풍기를 켜고 월패드에서 실제로 켜진 것을 확인했다. 상태도 다시 Home Assistant로 들어왔다.

## 이어서 정리한 것

- **환풍기를 쓰던 자동화:** 예전 통합의 환풍기 엔티티를 쓰던 자동화 두 개(환기 음성 안내, 2시간 후 자동 끄기)가 "알 수 없는 엔티티"로 멈춰 있었다. 새 엔티티로 바꿨다.
- **자동 현관 열기:** 벨이 울리면 문을 자동으로 여는 자동화가 남아 있었다. 지금은 센서가 없어 동작하지 않지만, 나중에 도어폰 라인을 연결하면 바로 살아날 수 있어서 지웠다.
- **현관문 열기:** 코콤 도어폰은 메인 라인과 다른 RS485 라인을 쓰고 체크섬 방식도 다르다(2바이트 CRC). 지금처럼 게이트웨이가 하나면 붙일 수 없어서 보류했다.
- **쓸모없는 조회:** 지운 기기를 주기적으로 조회하던 h2m 자동화 두 개를 정리했다.

## 확인한 결과와 남은 점

- 거실 난방: 수정 후 정상 값이 들어오는 것을 확인했다. 같은 증상이 다시 생기지 않는지는 더 지켜봐야 한다.
- 조명: 복구 후 켜고 끄기를 확인했다.
- 환풍기: 켜기·끄기와 상태 반영, 음성 안내를 확인했다. 풍량·모드 변경과 2시간 자동 꺼짐은 아직 확인하지 않았다.
