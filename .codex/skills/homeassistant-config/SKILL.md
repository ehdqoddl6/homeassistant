# Home Assistant 설정과 자동화

이 저장소의 `AGENTS.md`를 따른다. 아래 파일 경로는 저장소 루트 기준이다.
시작할 때 `docs/environment.md`, 관련 설정, `docs/history/README.md`에서 연결된 관련 이력을 읽는다.

## 요구와 적용 위치 파악

- 사용자 요청을 발동 조건, 실행 조건, 동작, 종료·재실행 조건으로 정리한다.
- 버전, 엔티티 ID, 상태·속성, 실제 include 구조와 UI/파일 관리 여부를 확인한다. 문서에서 확인할 수 있는 정보는 다시 묻지 않는다.
- 정보가 부족하면 독립적으로 가능한 초안·조사를 진행하고, 동작을 결정하는 누락 정보만 질문한다. 미확인 엔티티는 예시로 표시한다.
- UI의 단일 자동화 YAML, 자동화 목록 파일, `configuration.yaml` 내부 블록, 패키지의 최상위 구조를 구분한다. 붙여 넣는 위치에 맞는 형태로 작성한다.

## 작성과 수정

- 기존 파일 배치와 ID를 보존한다. `config/` 아래 새 파일을 만들면 이를 읽는 include 관계도 함께 다룬다.
- UI 관리 `automations.yaml`의 직접 편집을 기본값으로 삼지 않는다. UI YAML 편집기로 전달할 블록인지 별도 파일 관리 자동화인지 먼저 결정한다.
- 해당 Home Assistant 버전의 공식 문서를 확인해 문법을 선택한다. 단순 문법 최신화를 이유로 관련 없는 설정을 재작성하지 않는다.
- 자동화의 중복 실행과 취소 동작에 맞게 `mode`를 정한다. 지연·대기, 반복 트리거, 조건 불충족, 재시작 때의 동작 중 해당 시나리오에 영향을 주는 부분을 확인한다.
- 템플릿은 `unknown`, `unavailable`, 빈 값과 형 변환 실패를 고려한다. 잘못된 상태를 무조건 `0`으로 바꿔 위험한 동작을 만들지 않는다.
- 자격 증명은 파일 기반 YAML에서 지원되는 경우 `!secret`으로 분리한다. UI YAML 편집기에 `!secret`을 그대로 넣지 않는다. 실제 값 대신 필요한 키 이름을 기록한다.

## 검증과 전달

1. 변경 범위의 들여쓰기, 중복 키, 목록·매핑 형태와 include 대상 존재 여부를 검사한다. `!include`·`!secret`을 모르는 일반 YAML 파서의 오류와 HA 설정 오류를 구분한다.
2. 환경에서 가능한 Home Assistant 구성 검사를 수행한다. 설치 방식과 실행 경로가 확인되기 전에는 특정 CLI 명령이 동작한다고 가정하지 않는다.
3. 동작 확인이 요청·허용된 경우 실제 트리거와 조건을 포함한 시나리오를 확인한다. 액션 수동 실행만으로 트리거 검증을 통과 처리하지 않는다.
4. 수행한 검사와 미실행 검사를 분리해 알린다. 코드 검토·문법 검사만 했으면 그 수준만 표시한다.
5. `docs/templates/change.md`를 사용해 변경 이유, 파일, 검증 결과, 적용 위치, 운영 반영 여부, 복구 방법을 기록하고 히스토리 목록을 갱신한다.

결과는 변경 파일, 핵심 동작, 검증 결과, 적용 방법 순으로 간결하게 전달한다.
설정 작성 요청만으로 서버에 적용하거나 기기를 제어하지 않는다. 이미 허용된 적용 범위는 다시 승인받지 않는다.

## 필요할 때 확인할 자료

- [자동화 YAML](https://www.home-assistant.io/docs/automation/yaml/): 구성 위치와 자동화 항목
- [비밀정보 관리](https://www.home-assistant.io/docs/configuration/secrets/): `!secret`과 UI 편집 제약
- 버전에 따른 세부 동작은 위 문서에서 연결된 트리거·액션·템플릿 문서와 해당 버전 릴리스를 확인한다.
